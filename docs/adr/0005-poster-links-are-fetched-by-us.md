# A poster link is fetched by us, and the bytes decide what it is

The **playlist poster** (see `CONTEXT.md`) could already be set from a browser file upload. It can now also be set from a **link**, because the image you want is usually already on the web — a show poster on setlist.fm, album art on a fan site — and the alternative is a save-then-upload round trip through the Finder for a file you never wanted on disk.

Two decisions make that work, and neither is the obvious one.

**We dereference the link ourselves.** `plexapi`'s `uploadPoster(url=...)` will happily take a URL and let the Plex server fetch it, which is less code and no bytes through us. We rejected it. Handing the URL to Plex means `check_poster` never sees the image, so the type and size policy that governs uploads would simply not apply to links — the same feature with two different rule sets depending on which box you filled in. It also moves the fetch onto the Plex server's network, which is a different network from the app's (see ADR-0004 on why those two are not interchangeable here), and returns nothing we can turn into a useful message. A link that 404s would fail silently inside Plex. Fetching it ourselves costs one streamed download and buys one policy, one code path, and an honest answer for the user.

**The bytes decide the type, not the `Content-Type`.** A declared mimetype is not evidence. S3 serves perfectly good JPEGs as `application/octet-stream`, a CDN error page arrives as `image/jpeg` with a `200`, and a browser's upload mimetype is only ever a guess from the file extension. So `sniff_image_type` reads the leading twelve bytes and matches a magic number, and its answer — not anything the peer said — is what feeds `check_poster`. This applies to **both** paths: the upload field now sniffs too, so a renamed `.jpg` that is really a PDF is declined the same way on both. WebP needs care, being a RIFF container: matching only `RIFF` would also accept WAV and AVI, so the check reads `RIFF` *and* the `WEBP` tag at offset 8.

## Considered options

- **`uploadPoster(url=...)`, let Plex fetch.** Rejected above: no validation, no error surface, wrong network.
- **Trust `Content-Type` on the response.** Rejected: it is self-reported by the peer and routinely wrong in both directions. It would let an HTML error page through as an image and reject valid images served as octet-stream.
- **Trust `Content-Length` for the size check.** Rejected: frequently absent (chunked responses) and occasionally a lie. The cap is enforced against bytes actually read.
- **One field that takes either a file or a link.** Rejected: `<input type=file>` and a text box cannot be the same control, and faking it in JS would leave no-JS users with nothing.

## Consequences

- `fetch_poster_link(link) → (poster_path, reason)` returns the **same shape** as the web layer's upload helper — a temp file the caller must delete, or a short reason — so all three write paths keep one `finally: _cleanup_poster(...)` and one warning helper. Nothing downstream of `_take_poster` knows which box the image came from.
- The size cap is enforced **inside the streaming loop**, breaking the moment the accumulated bytes exceed `POSTER_MAX_BYTES`. This is not an optimisation. Without it, a link that never ends is buffered until the process dies, and the app has no request size limit to fall back on — ADR-0002 deliberately declines `MAX_CONTENT_LENGTH`. The comparison matches `check_poster`'s exactly (`>`, not `>=`) so an image sitting on the limit is accepted by both paths.
- Network failure is a **declined poster, not an exception**. A bad link is the most likely mistake this feature invites, so a 404, a DNS failure or a timeout returns `(None, "couldn't be fetched")` and is logged. Best-effort inherits wholesale from ADR-0002: the playlist is still created or saved, and the user gets the same soft warning as any other image problem. `POSTER_LINK_TIMEOUT` bounds the wait so a dead host can't hold a save open.
- Only `http` and `https` links are fetched. `requests` would already reject `file://` with an `InvalidSchema` that our handler catches, but relying on that leaves the guard implicit in a dependency's behaviour, so it is stated in our own code.
- **A usable file wins when both boxes are filled.** A picked file is a deliberate act in a way a leftover string in a text input is not — you can navigate back to a form with a link still populated, but never with a file still attached. The client hides the link box once a file is chosen so the two never silently compete. But precedence applies only among images we can actually use: a file that fails `check_poster` **falls through to the link** rather than consuming the attempt, and the client reveals the link box again when it flags one. The rejected alternative — first field supplied wins outright — produced the worst screen in the feature: an unusable file, a good link hidden from view, and no image set, with nothing on the page explaining why.
- We do **not** filter private or loopback addresses out of the link. This app binds `127.0.0.1`, is unauthenticated, and holds a Plex token in its config; anyone who can reach the form can already read that token, so a URL fetcher is not the weakest thing here. Filtering would also break the legitimate case of pulling art off your own NAS. This reasoning holds *only* while the app stays local — if it ever grows real users or a shared deployment, this is the decision to revisit first, before the token one.
