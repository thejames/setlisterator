# A song's default version comes from the earliest album, not the most cohesive one

When a setlist song exists on several albums in the library, the version picked by default is the one on the **earliest album** — the oldest-dated album carrying that song (see `CONTEXT.md`). Candidate order is: an explicitly named **preferred album** first, then title match tier, then album year ascending, then library order.

This reverses `239fe7e`, which answered the same complaint the other way. That commit's problem statement — *"a song you own on both a studio release and a full live recording of the show resolved to an arbitrary version"* — is precisely the complaint that prompted this decision; only the direction was wrong. It measured which album covered the most of the setlist and, past a threshold, silently preferred it, on the assumption that matching a show means wanting that show's recording. In practice the wanted version is almost always the original studio one, and a cohesive album is usually a live record — so the auto-pick was wrong most of the time it fired, and wrong invisibly, because nothing on the page said a rule had been applied.

We rejected layering earliest-first *beneath* the auto-detected cohesion, keeping both rules. That preserves the live-recording case, but only by making the default two-part and unexplainable ("usually the earliest, unless one album covers most of the show"), and it forces a third selectable strategy into the preview dropdown so users can get back to plain earliest — a new form value threaded through `/preview`, `/rematch`, and `gather_matches`, carried solely to preserve a behaviour nobody asked for. Removing the auto-pick collapses all of it.

Cohesion detection itself is kept, demoted from a decision to a **suggestion**. `_album_coverage` still ranks albums by how much of the setlist they cover, and that ranking still populates the preview dropdown — so a full live recording of the show appears at the top of the list with its song count. It is one click away instead of imposed.

## Consequences

- `_auto_album` and its `ALBUM_COHESION_MIN_FRACTION` / `ALBUM_COHESION_MIN_SONGS` constants are deleted. `gather_matches` reduces to `preferred_album = prefer_album or ""`, so passing `None` and `""` no longer differ — there is nothing left to auto-detect.
- Album year is read from the **track**, not by fetching the album. Plex sends `parentYear` on every `<Track>` on both endpoints the matcher uses (`allLeaves` for the artist-scoped path, `sections/<id>/all?type=10` for the global fallback), and sends no `year` attribute at all. So year costs zero extra requests and covers both match paths.
- plexapi 4.18.1 does not map `parentYear` onto `Track` (`Track._loadData` reads only `year`), so it is reached through the raw element: `track._data.attrib`. A `_track_year(track)` helper isolates that, probing `getattr(track, "parentYear")` first — which future-proofs against plexapi adding the attribute and lets offline test fakes set a plain attribute, as they already do with `parentTitle` for `_track_album`.
- The `year` fallback is read from that same raw element, **never** as `getattr(track, "year")`. plexapi *does* define `year` on `Track` and leaves it `None` here, and `PlexPartialObject.__getattribute__` reloads any public attribute it finds `None` on a partial object — so an innocent-looking `track.year` costs one HTTP round-trip per candidate, and can raise from inside a sort. That is precisely the "no extra requests" rule this decision is built on, inverted. Names starting with `_` are exempt from the reload, which is what makes `_data` safe.
- Depending on private plexapi state is accepted because the failure mode is quiet, not fatal: if `_data` ever disappears, every candidate resolves to unknown year and ordering falls back to today's behaviour. A debug log when a whole setlist resolves zero years keeps that discoverable.
- An album with **no year sorts last**, never first, keeping its library order among other undated candidates. Undated means unknown, not old; floating undated albums to the top would let the worst-tagged album in the library win by default. A `year` of `0` or negative counts as unknown.
- Year sorts **within** a title tier, never across one. A better title always beats an older album, because the titles that fall into loose/medley/prefix are overwhelmingly live cuts, remasters, and alternate takes — the population earliest-first exists to avoid.
- No medley guard is needed, unlike `_prefer_album_first`, which needs its explicit one because album preference jumps *above* tier. Medley is its own tier, so year ordering only sorts medleys amongst themselves.
- The preview dropdown's first option becomes **Earliest album**, always pre-selected. A true "no preference" — Plex's arbitrary `artist.tracks()` order — is no longer reachable. It was never a preference, only the absence of one, and existed as the default only because nothing better did.
- The rule is literal: the earliest album, not an inference about which release is "official". A single that predates its album wins, and a remaster dated later than a live album loses. Detecting studio-vs-live-vs-compilation would need signals Plex does not reliably provide (`Album.subformats` / `styles` are agent-dependent) or title heuristics, and a wrong-but-consistent rule is easier to live with than a clever one that surprises. Both cases are one click from fixed via the dropdown, the per-row picker, and audition.
- `Album.year` is preferred over `originallyAvailableAt` in principle as well as in practice: reissue metadata splits original and edition dates across the two inconsistently by agent, so the extra precision would buy noise.
- `_prefer_album_first` is unchanged. An explicitly named album still outranks tier — that is the manual override for "I prefer this track on *that* record".
- The CLI gains no flag and changes silently: it passes no preference, so it moves from cohesion auto-detect to earliest-first.
- Regression by design: matching a show you own a full live recording of now yields studio versions until you pick that album from the dropdown. This is the case `239fe7e` was written for, and it is being traded away deliberately.
