# Refresh the Plex playlist summary when missing tracks are added

Status: done
Category: bug
Reported: 2026-07-24
Implemented: 2026-07-24 (2026.7.3)

## Request

When a playlist created via the setlist creator is updated — because tracks that
were previously missing have since been located or purchased — the summary
written to the Plex playlist should be updated to reflect the new missing-track
information.

## Triage Notes

**Verification: confirmed.**

`create_playlist` writes a summary to Plex via `_playlist_summary` +
`playlist.editSummary`. `add_to_playlist` — the Update path — never calls
either. It *does* pass fresh `history_meta` to `_record_history`, so the history
JSON's `missing_tracks` is correctly emptied while the Plex summary still
advertises the track as missing.

Reproduced against the existing fake-Plex test harness: create a 2-of-3 playlist
with "Destiny Unbound" missing, then `add_to_playlist` the bought track with
`missing_tracks: []`.

```
--- summary after update ---
2 of 3 songs added.

Missing (1):
  • Destiny Unbound

Source: u
Created by Setlist-er-ator. 🤘

history missing_tracks: []
```

History is fresh; the Plex summary is stale. Two sources of truth disagree, and
the one the user actually reads is the wrong one.

**Redundancy check: not already implemented.** Searched the core module, the web
module, and the templates for the domain concept (`summary`, `editSummary`).
Every write is inside `create_playlist`. `set_playlist` (the editor path) writes
no summary at all. Tests cover `_playlist_summary` as a pure function and on the
create path only — no test exercises the summary after an update, because there
is no behaviour to test.

**Prior rejection check: none.** No `.out-of-scope/` knowledge base exists yet.

**Two secondary gaps found while verifying:**

1. The update template never submits a `song_count` field (only the preview
   template does), so `_history_meta_from_form` yields `song_count: 0` on the
   update path and any total falls back to `added + missing`.
2. Neither template submits the *titles* of songs the user unchecked. The forms
   post only the included positions and their picked rating keys, so the server
   learns what was kept and never what was dropped.

## Decisions taken during triage

- **"Declined" is derived, not remembered.** Defined as: matched in the library,
  but not in this playlist. Recomputed at every summary write from stored match
  data plus live playlist membership, so it self-heals regardless of which path
  last touched the playlist — including edits made directly in Plex. See the
  glossary entry added to `CONTEXT.md`.
- **Match data is stored in history, not re-derived from the matcher.** The
  history entry gains a per-song map so the editor can write a correct summary
  without any matcher call. Only the Update path, which already re-matches,
  refreshes that map.
- **Format:** show header, a counts line, then Missing and Declined as
  separately labelled self-explaining sections.

## Agent Brief

**Category:** bug
**Summary:** A playlist's Plex summary is written once at create time and never
refreshed, so it keeps advertising tracks as missing after the user has bought
them and added them via Update.

**Current behavior:**

Only the create path writes a summary to the Plex playlist. The Update path
(add-only top-up of an existing playlist) refreshes the history entry's
missing-track data but leaves the Plex summary untouched, so it goes stale the
moment a previously-missing track is added. The editor path (rename + set exact
ordered membership) writes no summary at all.

The summary currently reports a single "N of M songs added." line plus a
`Missing` list. It has no concept of a song that is present in the library but
deliberately not in the playlist — the existing tests call that "excluded" in
comments, but it is invisible in the output.

**Desired behavior:**

Every setlist-sourced song falls into exactly one of three states, derived fresh
each time a summary is written:

- **added** — its matched track is currently in the playlist
- **declined** — it matched a library track, but that track is not in the
  playlist
- **missing** — it never matched anything in the library

The summary is rewritten from those three states on the create path, the Update
path, and the editor path. Format:

```
Phish · Madison Square Garden
2023-12-31

15 songs · 13 added · 1 declined · 1 missing

Missing (1) — not in your library:
  • #7 Destiny Unbound — Lawn Boy

Declined (1) — in your library, not added:
  • #4 Wilson — Junta

Source: https://www.setlist.fm/...
Created by Setlist-er-ator. 🤘
```

Edge cases:

- A section is omitted entirely when its list is empty; its count is omitted
  from the counts line too (`15 songs · 15 added.`).
- When every song is added, the existing "This is the full run of the show."
  note is retained.
- A medley — two setlist positions resolving to the same track — counts as two
  songs added, and keeps the existing "some songs share a recording" note
  reconciling the count with the playlist's item count.
- Manually-built playlists (no setlist behind them) still get no summary, and an
  update must **skip** the write rather than blank an existing summary when the
  generated text is empty.
- History entries predating the per-song map have no match data. Leave their
  summaries untouched rather than writing a degraded one; the next Update
  backfills the map and the summary becomes correct from then on.
- The editor operates on any Plex playlist, including ones this app never
  created. Those have no history entry and must be left alone.
- Writing the summary stays **best-effort** on every path, consistent with the
  existing poster policy: a failure logs a warning and never undoes or blocks
  the create, update, or edit that triggered it.

**Key interfaces:**

- The history entry gains a per-song map — one record per setlist position
  carrying at minimum the position, the song title, the album (for the buy
  list), and the matched Plex `rating_key` or null when nothing matched. This is
  what makes `declined` derivable without a matcher call.
- `_playlist_summary` (or its successor) should take the per-song map and the
  playlist's current membership rather than a bare `added_count`. It returns ""
  when there is nothing meaningful to say, and callers skip the write on "".
- The Update path must refresh the per-song map, since it is the only path that
  re-matches and therefore the only one that can discover a newly-purchased
  track.
- The web layer's form-to-history-meta helper needs `venue`, `city`, and
  `song_count` available on both the preview and update forms. Venue and city
  are already parsed from setlist.fm by the show parser and used to build the
  default playlist name — they are simply not threaded into the forms or
  history yet.
- The editor's save path currently receives no setlist context. It should locate
  its history entry by the playlist's rating key and no-op cleanly when there
  isn't one.

**Acceptance criteria:**

- [ ] After an Update that adds a previously-missing track, the Plex summary no
      longer lists that track under Missing, and its counts reflect the new state
- [ ] A song matched in the library but not in the playlist appears under
      Declined, with its position and album
- [ ] Unchecking a song at create time puts it under Declined, not Missing
- [ ] Removing a track via the editor moves that song from added to declined in
      the summary, with no matcher or setlist.fm call made
- [ ] The counts line, the section headers, and the number of bullets under each
      section always agree with each other
- [ ] A fully-added playlist shows the "full run" note and no Missing or
      Declined sections
- [ ] A medley counts as two songs added and retains the shared-recording note
- [ ] Manual playlists get no summary; an update never blanks an existing summary
- [ ] Editing a playlist with no history entry leaves its summary untouched
- [ ] A Plex failure while writing the summary logs a warning and leaves the
      create/update/edit itself successful
- [ ] Tests are offline, monkeypatching Plex the way the existing suite does; the
      full suite passes

**Out of scope:**

- Re-matching from the editor path. The editor must not gain setlist.fm network
  access or trigger a full library scan; discovering newly-purchased tracks
  remains the Update path's job.
- Backfilling the per-song map into existing history entries as a migration
  step. It fills in naturally on the next Update.
- Changing what the matcher considers a match, or any tier/quality behaviour.
- Surfacing declined songs anywhere in the web UI. This issue changes only the
  text written to Plex.
- The Buy list and its album-caching behaviour.

## Comments

> *This was generated by AI during implementation.*

**Done.** All acceptance criteria met; 220 tests pass offline.

Two defects were caught by the `/code-review` pass and fixed before commit —
both were real, and both are now covered by regression tests verified to fail
without their fix:

1. **The CLI create path silently lost its summary.** Only the web forms were
   threaded with the per-song map, so `main()` built `history_meta` without one
   and `_playlist_summary` correctly returned "" — meaning CLI-created playlists
   went from having a summary to having none. Root cause was map-building living
   in the web layer; fixed by extracting `song_map(result)` into core and
   calling it from both surfaces. Covered by
   `test_main_writes_a_summary_for_a_cli_created_playlist`.
2. **The update path derived its summary before reconciling the map.**
   `_merge_song_maps` ran inside `_record_history`, which happens *after* the
   summary write, so a version the user selected at create time was displaced by
   the re-match's default and that song read as declined. The merge now happens
   in `add_to_playlist` before anything reads the map, and `_record_history` no
   longer merges at all (a fresh create must keep its own selections). Covered by
   `test_update_keeps_hand_picked_version_over_rematch`.

**Two deviations from the brief, both deliberate:**

- **`song_count` was deleted rather than threaded onto the update form.** The
  brief asked for it, but the per-song map makes the setlist length `len(songs)`,
  and nothing else ever read the field — it was already dead everywhere it
  appeared. Half-threading a dead field would have been worse than removing it.
- **The show header includes the city** (`Primus · The Fillmore, San Francisco`),
  where the approved format preview showed only artist and venue. Venue names
  repeat across cities, and the brief asked for city to be threaded regardless.
  Trivial to drop if it reads as noise in Plex.

**Known limitation, not fixed:** swapping a track for a different version *in the
editor* leaves the map pointing at the old key, so that song reads as declined
and the new track goes unaccounted. The editor has no setlist context to
re-match with, and doing so was explicitly out of scope. Running Update repairs
it. Worth its own ticket if it bites.
