# Default to the earliest album when a song is on several

Status: ready-for-agent
Category: enhancement
Reported: 2026-07-29 (user request)
Triaged: 2026-07-30

## Request

> Hey, I've got an idea for song matching. Usually, I want the earliest version,
> because that's the official release / album version. Can you have it match
> songs to the earliest release (as the default)?

## Triage Notes

**Redundancy check: not already implemented.**

Searched by domain concept rather than wording — `year`, `originallyAvailableAt`,
`parentYear`, `release`, `album` — across the core module, the web module, the
templates and the client script. **No release-date data is read from Plex
anywhere in the app.** `_track_album` pulls `parentTitle` and nothing else; no
code path touches a year.

The only version-biasing mechanism is **preferred album**, by album title:
`_prefer_album_first` stable-reorders a song's candidates so matches on one named
album lead, and `_auto_album` picks that album automatically when one album covers
≥50% and ≥3 of the setlist's matched songs. Absent a preferred album, candidate
order comes from `_ranked_matches`: title tier first, then — because the sort is
stable — whatever order `artist.tracks()` returned from Plex. That is arbitrary
from the user's point of view, which is what prompted the request.

**Prior rejection check: none.** No `.out-of-scope/` knowledge base exists.

**The finding that reframed this issue.** `_auto_album` arrived in `239fe7e`
("feat: prefer a cohesive album when a song exists on several you own"), whose
problem statement is *the same complaint*:

> a song you own on both a studio release and a full live recording of the show
> resolved to an arbitrary version

That commit answered it by preferring the recording of the show. The maintainer
confirms during triage that this was never the intent and is almost never wanted
— the wanted version is the original studio one. So this issue is not a feature
stacking on top of an existing rule; it is the second, correct answer to a
question already asked once, and it **reverses** the first one.

**Data availability: verified against the live server.** Plex sends
`parentYear` on every `<Track>` element and **no** `year` attribute, on both
endpoints the matcher uses — `/library/metadata/<artist>/allLeaves` (the
artist-scoped path, via `artist.tracks()`) and
`/library/sections/<id>/all?type=10` (the global fallback, via `searchTracks`).
So the album's year rides along on tracks we already fetch: zero extra requests,
both match paths covered, no album objects needed.

plexapi 4.18.1 does not map it — `Track._loadData` reads `year`, never
`parentYear` — so `track.year` is `None` on this server. The value is reachable
only through the raw element (`_data.attrib`), which `PlexObject.__init__` sets
and `reload` preserves.

## Decisions taken during triage

Recorded as `docs/adr/0006-earliest-album-is-the-default-version.md`; glossary
entry **Earliest album** added to `CONTEXT.md`, and **Preferred album** revised to
say it is now only ever explicitly chosen.

- **The cohesive-album auto-pick is removed, not layered under.** Layering
  earliest beneath it makes the default two-part and unexplainable, and forces a
  third selectable strategy plus a new form value through `/preview`, `/rematch`
  and `gather_matches` — all to preserve a behaviour nobody asked for. Cohesion
  detection survives as a *suggestion*: the dropdown still lists albums by
  coverage, so a live recording of the show is one click away instead of imposed.
- **The rule is literal — earliest album, not "the official release".** Those
  diverge (a single predates its album; a remaster is dated later than a live
  record). Detecting studio-vs-live-vs-compilation needs signals Plex doesn't
  reliably give, and a wrong-but-consistent rule beats a clever one that
  surprises. Every miss is one click from fixed.
- **Year breaks ties beneath title tier, never above it.** The titles that fall
  into loose/medley/prefix are overwhelmingly live cuts, remasters and alternate
  takes — the population earliest-first exists to avoid.
- **Undated albums sort last, never first.** Undated means unknown, not old.
- **Earliest is the floor; a true "no preference" is dropped.** It was never a
  preference, only the absence of one.
- **Private plexapi state is acceptable here** because the failure mode is quiet:
  if `_data` disappears, everything resolves to unknown year and ordering falls
  back to today's behaviour.

## Agent Brief

**Category:** enhancement
**Summary:** When a setlist song exists on several albums in the library, default
to the version on the oldest-dated album, and stop auto-preferring the album that
covers most of the setlist.

**Current behavior:**

Candidate versions for a setlist song are ranked by title match tier
(exact → loose → medley → prefix) and nothing else, so two equally-good title
matches on different albums resolve in whatever order the Plex library returned
them. No release-date data is read from Plex at all.

Separately, when one album supplies at least half and at least three of the
setlist's matched songs, that album is detected and silently applied as the
preferred album, floating its versions above title tier. This targets the case
where the library holds a full live recording of the show being matched. It is
being removed.

**Desired behavior:**

Candidate order becomes: an explicitly named preferred album first (unchanged),
then title match tier, then **album year ascending**, then library order.

- Two candidates at the same tier resolve to the one on the older album.
- A candidate whose album year is unknown sorts after every dated candidate, and
  undated candidates keep their existing relative order. A year of `0` or
  negative counts as unknown.
- Equal years keep their existing relative order.
- A better title always wins over an older album: an exact match on a 2011 album
  still beats a loose match on a 1975 album.
- Medleys are unaffected beyond being sorted amongst themselves — year must never
  float a medley above a cleaner title match. No explicit guard should be needed
  if year sorts strictly within a tier; if the implementation makes year cross
  tiers, it is wrong.
- No album is auto-preferred any more. A setlist where one album covers most of
  the songs comes back with no preferred album, and its default versions are the
  earliest ones.
- The albums-by-coverage list that populates the preview dropdown is unchanged, so
  that album still appears there, still first, still labelled with its song count.
- The dropdown's first option — currently "No preference" — becomes
  **"Earliest album"** and is selected whenever no album is preferred. Selecting
  an album still overrides, and re-match on switching albums still only re-orders
  untouched rows.
- The CLI needs no new flag; passing no preference now means earliest-first.
- Where no candidate for a setlist resolves a year, ordering must be identical to
  today's, and that condition should emit a debug-level log so a silent
  regression is discoverable.

**Key interfaces:**

- A new helper resolving one track's album year — returns a positive `int` or
  `None`, and never raises. It must probe a `parentYear` *attribute* first (so
  offline test fakes can set one plainly, as they already do with `parentTitle`
  for `_track_album`, and so it starts working automatically if plexapi ever maps
  the attribute), then fall back to the raw plexapi element's `attrib`, then to a
  `year` attribute.
- The ranked-candidate ordering (`_ranked_matches` and anything reading it) gains
  album year as a sort key **below** the existing tier/artist rank and **above**
  input order. The sort must stay stable so equal keys keep library order.
- `_prefer_album_first` — unchanged. A named album still outranks tier.
- `_auto_album` and its two cohesion constants — deleted.
- `_album_coverage` — unchanged; it still produces the by-coverage album list.
- `gather_matches` — the `prefer_album=None` auto-detect branch goes away, leaving
  `None` and `""` equivalent. Its return shape is unchanged: `preferred_album` and
  `album_options` are still present, with `preferred_album` now empty unless the
  caller named one. Update the docstring, which currently documents auto-detection.
- No extra Plex requests may be introduced. Album year must come from the track
  objects already fetched, not from fetching albums.

**Acceptance criteria:**

- [x] Two same-tier candidates on albums dated 1975 and 1991 default to the 1975 one
- [x] A candidate with no album year sorts after every dated candidate; undated
      candidates keep their relative order among themselves
- [x] A year of `0` or a negative year is treated as unknown, not as very old
- [x] An exact-tier match on a newer album still beats a loose-tier match on an
      older one
- [x] A medley-tier candidate is never ordered above an exact- or loose-tier
      candidate on a newer album
- [x] A setlist where one album covers most of the matched songs returns an empty
      `preferred_album`, and its songs default to their earliest versions
- [x] That album is still present and still first in the by-coverage album list
- [x] Explicitly naming an album still floats its versions above title tier
- [x] The preview dropdown's first option reads "Earliest album" and is selected
      when no album is preferred
- [x] A CLI run with no flags picks earliest versions
- [x] A fake track exposing only `parentYear` orders correctly, proving the year
      is read without fetching albums
- [x] When no candidate resolves a year, candidate order is unchanged from the
      pre-change behaviour, and a debug log records it
- [x] The cohesion auto-detection tests from `239fe7e` are deleted or inverted to
      assert no auto-pick
- [x] Tests stay offline, monkeypatching Plex the way the existing suite does; the
      full suite passes

**Out of scope:**

- Detecting whether an album is live, a compilation, or a remaster, by any means —
  metadata flags, subformats, styles, or title heuristics.
- Fetching `Album` objects or using `originallyAvailableAt`. Year comes from the
  track only.
- Showing the album year anywhere in the UI. It would help verify a pick and is a
  reasonable follow-up, but it was not decided during triage — don't add it here.
- Making the album preference per-song. The dropdown stays setlist-wide; per-song
  overrides are what the existing per-row version picker is for.
- Persisting a version-selection preference per browser or via env var (a gear-menu
  toggle, `MATCH_PREFER`). Considered during triage and deferred: the decision's
  natural scope is one show, not one user.
- Changing the matcher's tiers, normalization, or what counts as a match.
- Removing or restructuring the "Prefer album" dropdown beyond the relabelled
  first option.

## Comments

**2026-07-30 — implemented.** One deviation from the Agent Brief, in
`_track_year`'s probe order. The brief asked for "then to a `year` attribute" as
the third probe; that probe is instead read from the raw element's `attrib`
alongside `parentYear`. Reason: plexapi defines `year` on `Track` and leaves it
`None` on this server, and `PlexPartialObject.__getattribute__` reloads any
public attribute it finds `None` on a partial object — so `getattr(track,
"year")` would fire one HTTP request per candidate (breaking "No extra Plex
requests may be introduced") and could raise out of the sort (breaking "never
raises"). Underscore-prefixed names are exempt from that reload, so `_data`
stays free. ADR 0006 records this; `test_ordering_uses_the_raw_element_and_costs_no_requests`
pins it with a fake that counts reloads.
